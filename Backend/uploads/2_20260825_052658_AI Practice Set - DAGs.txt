# Practice Worksheet: Directed Acyclic Graphs in AI

## Introduction
Directed Acyclic Graphs (DAGs) are fundamental structures in artificial intelligence, particularly in probabilistic graphical models, causal inference, and the execution of computational tasks. A DAG consists of nodes representing variables or operations and directed edges representing dependencies or relationships, with the critical constraint that no cycles exist. This worksheet explores the theoretical properties, computational implications, and practical applications of DAGs.

## Problems

3. In the context of Bayesian Networks, why is the acyclic property essential for defining a valid joint probability distribution over the variables?

### Problem 3: Causal Inference and d-Separation

# Answer Guide

## Problem 1: Conceptual Foundations
1. A DAG must not contain any directed cycles. This means there is no sequence of edges that starts and ends at the same node.
2. Adding C -> A creates a cycle: A -> B -> C -> A. This violates the acyclic property. In a DAG, you cannot return to a starting node by following the direction of the edges.
3. In Bayesian Networks, the joint probability is defined as the product of conditional probabilities for each node given its parents. If a cycle existed, a variable would depend on itself indirectly, creating a circular definition that makes the probability distribution undefined or requiring complex equilibrium assumptions not present in standard Bayesian Networks.

## Problem 2: Topological Sorting
1. A topological sort is a linear ordering of vertices such that for every directed edge u -> v, vertex u comes before v in the ordering.
2. One valid ordering is: X, B, H, O. Another is: B, X, H, O. The key is that X precedes H, H precedes O, and B precedes O. B and X can be in any relative order since they are independent.
3. Yes, a valid sort still exists. The new dependency B -> H does not create a cycle. The graph remains acyclic. A valid order would be: X, B, H, O.

## Problem 3: Causal Inference
1. The paths are: S -> L (direct) and S <- G -> L (indirect via G).
2. S and L are NOT d-separated given G. The path S <- G -> L is a "fork" at G. Conditioning on G opens this path, allowing association between S and L.
3. The edge G -> S and G -> L creates a common cause. If we do not condition on G, the path S <- G -> L is blocked (assuming no other variables). However, the direct path S -> L is always open. Therefore, S and L are dependent. If we condition on G, the indirect path is open, but the direct path remains open. Thus, S and L are dependent regardless.
4. Yes. The direct edge S -> L exists. Observing L provides information about S because S is a direct cause of L. The lack of knowledge about G does not block the direct causal link.

## Problem 4: Debugging a Computational DAG
1. There is no cycle in the described dependencies. The structure is a standard DAG.
2. The hang is likely due to a synchronization issue. Node G depends on E and F. Node E depends on D, and Node F depends on D. If the execution engine does not properly handle fan-out and fan-in synchronization, it might wait for a node that has already completed or fail to trigger G when both E and F are done. A common error is assuming a single predecessor.
3. The fix is to ensure the execution engine supports multi-parent nodes. If the engine is simplistic, introduce a dummy synchronization node. Create Node Sync_EF. Add edges E -> Sync_EF and F -> Sync_EF. Then change G's dependency to Sync_EF. This ensures G waits for both E and F to complete.

## Problem 5: Real-World Scenario
1. The critical path is the longest path from start to finish in terms of time. The DAG structure allows us to calculate the earliest start and latest finish times for each node. The critical path determines the minimum project duration.
2. The DAG structure only captures logical dependencies (data flow). It does not capture resource constraints (capacity). Two independent nodes might require the same resource, creating a conflict that is not visible in the graph topology.
3. Modify the scheduling algorithm to include resource availability checks. Instead of just checking if predecessors are done, the scheduler must also check if the required resource is free. This turns the problem into a resource-constrained project scheduling problem (RCPSP), which may require heuristics or integer programming beyond simple topological sorting.
