## 3. Core Concepts & Explanations  

### 3.1 What Is a Linked List?  

- **Dynamic, non‑contiguous** data structure composed of *nodes*.
- Each node stores **data** + **reference(s)** (pointers) to other nodes.
- The **head** pointer gives entry to the structure; the **tail** (optional) points to the last node or back to the head (circular).

| Property | Array | Linked List |
|----------|-------|-------------|
| Memory layout | Contiguous block | Scattered nodes (heap) |
| Random access | O(1) via index | O(n) by traversal |
| Insertion/Deletion | O(n) (shift) | O(1) if position known |
| Size flexibility | Fixed (or costly resize) | Naturally grows/shrinks |

### 3.2 Node Structure (language‑agnostic)

```text
+-----------+-----------+
|  data     |  next ptr |
+-----------+-----------+
```

- **Singly**: one `next` pointer.
- **Doubly**: `next` **and** `prev` pointers.
- **Circular**: last node’s `next` points to `head` (and `prev` to `tail` for doubly‑circular).

### 3.3 Variants & When to Use  

| Variant | Pointer Layout | Advantages | Disadvantages | Typical Use‑Case |
|---------|----------------|------------|---------------|-----------------|
| **Singly** | `next` only | Minimal memory, simple | No backward traversal, delete requires predecessor | Simple stacks, queues, adjacency lists |
| **Doubly** | `next` + `prev` | O(1) delete given node, reverse traversal | Extra memory, more pointer updates | Browser history, LRU cache, undo/redo |
| **Circular** | `next` (and optionally `prev`) with wrap‑around | No null terminator, easy round‑robin, constant‑time concatenation | Must guard against infinite loops | Music playlists, round‑robin scheduling, Josephus problem |

### 3.4 Core Operations (Pseudo‑code)  

#### 3.4.1 Insertion  

```pseudo
function insertFront(head, value):
    node = new Node(value)
    node.next = head
    head = node
    return head
```

- **After a given node** (requires pointer to that node):
  ```pseudo
  node.next = target.next
  target.next = node
  ```
- **At tail** (if tail pointer stored → O(1); otherwise traverse → O(n)).

#### 3.4.2 Deletion  

```pseudo
function deleteNode(head, key):
    if head == null: return null
    if head.data == key:
        temp = head
        head = head.next
        free(temp)          // C only
        return head
    prev = head
    cur  = head.next
    while cur != null and cur.data != key:
        prev = cur
        cur  = cur.next
    if cur != null:
        prev.next = cur.next
        free(cur)
    return head
```

#### 3.4.3 Search  

Linear scan → O(n). Return pointer to node or `null`.

#### 3.4.4 Traversal  

```pseudo
cur = head
while cur != null:
    process(cur.data)
    cur = cur.next
```

### 3.5 Complexity Summary  

| Operation | Best | Average | Worst | Remarks |
|-----------|------|---------|-------|---------|
| Insert front | O(1) | O(1) | O(1) | No traversal |
| Insert after node | O(1) | O(1) | O(1) | Requires node reference |
| Insert at tail (no tail ptr) | O(n) | O(n) | O(n) | Traversal needed |
| Delete (known node) | O(1) | O(1) | O(1) | With doubly linked list |
| Delete by value | O(n) | O(n) | O(n) | Need search |
| Search | O(n) | O(n) | O(n) | Linear scan |
| Space per node | O(1) | O(1) | O(1) | + pointer(s) |

### 3.6 Common Pitfalls  

| Pitfall | Symptom | Fix |
|---------|---------|-----|
| Forgetting to update `prev` in doubly list | Corrupted backward links → infinite loop or segmentation fault | Update both `next` and `prev` consistently |
| Using a freed node (C) | Crash, “use after free” | Set pointer to `NULL` after `free`, or use smart pointers (C++) |
| Not handling `null` in circular list | Endless loop in traversal | Detect loop by counting nodes or using a sentinel |
| Off‑by‑one when inserting at tail without tail pointer | Last node’s `next` stays `null` → list appears truncated | After traversal, set `last.next = newNode` and `newNode.next = null` (or head for circular) |
| Memory leak (Java/Python) by retaining obsolete references | GC cannot reclaim → high memory usage | Nullify references after deletion |

## 4. Discussion Questions  

1. **Design Choice:**  
   *If you were implementing a browser’s back/forward history, would you choose a singly, doubly, or circular list? Justify your answer in terms of operation cost and memory.*  

2. **Amortised Analysis:**  
   *Suppose we maintain a tail pointer for a singly linked list. Inserting at the tail is O(1). However, if we occasionally need to “reset” the tail after a bulk deletion, how does this affect the amortised cost?*  

3. **Cache Locality:**  
   *Arrays benefit from spatial locality; linked lists do not. In what scenarios does this disadvantage outweigh the O(1) insertion benefit?*  

4. **Hybrid Structures:**  
   *Can you think of a data structure that combines the strengths of arrays and linked lists? (e.g., unrolled linked list, skip list). Briefly describe it.*  

5. **Safety in Modern Languages:**  
   *How do languages with automatic memory management (Java, Python, Rust with ownership) mitigate the classic linked‑list bugs? Discuss any remaining risks.*

## 5. In‑Class Activities  

### 5.1 Warm‑Up Pair‑Programming (5 min)  
- **Task:** Write the `Node` class/struct in the language of the day, including a `__str__`/`toString` method for debugging.  
- **Goal:** Ensure every student can instantiate a node and print its contents.

### 5.2 Group Annotation (8 min)  
- Provide a printed snippet that inserts a node at the tail **without** a tail pointer.  
- **Students:** In groups of three, label each line with its time complexity and identify any missing null‑checks.  
- **Outcome:** Reinforces O‑notation and defensive coding.

### 5.3 Debugging Challenge (7 min)  
- Distribute a buggy `deleteNode` routine (e.g., missing `prev.next = cur.next` update).  
- **Pairs:** Run the code on a small list (1→2→3) and locate the runtime error.  
- **Instructor:** Walk around, prompting “What does the pointer diagram look like after this line?”

### 5.4 Algorithmic Mini‑Project (10 min) – *Remove Duplicates*  

**Problem Statement:**  
Given an unsorted singly linked list, delete all duplicate values, preserving the first occurrence.

**Two Approaches to Discuss:**  

| Approach | Data‑Structure Used | Time | Space |
|----------|--------------------|------|-------|
| Brute‑force (nested loops) | None | O(n²) | O(1) |
| Hash‑set tracking | `HashSet`/`unordered_set` | O(n) | O(n) |

- **Activity:** Each group writes pseudo‑code for one approach, then swaps with another group for peer review.  
- **Deliverable:** One‑sentence description of why their chosen method is preferable in practice.

### 5.5 Exit Ticket (2 min)  
- Prompt: *“Write, in one sentence, the most important advantage of a doubly linked list over a singly linked list.”*  
- Collect on sticky notes or via a quick online poll.

## 6. Homework Assignment  

1. **Implementation:**  
   - Implement a **circular doubly linked list** with the following public methods: `pushFront`, `pushBack`, `popFront`, `popBack`, `find(value)`, `remove(node)`.  
   - Include a `display()` that prints the list forward and backward.

2. **Complexity Proof:**  
   - Write a short (≈200 words) justification for the O(1) amortised cost of `pushBack` when a tail pointer is maintained.

3. **Application Problem:**  
   - Given a stream of integers, maintain a linked list that always holds the **last k** elements (sliding window). Provide code and explain how you achieve O(1) per insertion and deletion.
